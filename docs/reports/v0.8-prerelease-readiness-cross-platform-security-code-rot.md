## 10. Security audit

### 10.1 A confirmed, fixed finding: symlinked media file escape

**SEC-1 (CRITICAL, fixed).** `src/viewerServer/evidence/mediaResolver.ts`'s
`checkExists()` used `fs.stat()`, which follows symlinks. The upstream
containment check (`resolveContainedFile`) only proves the *filename* is a
safe bare name inside an already-contained artifact directory - it never
proves that filename isn't itself a symlink/junction whose target resolves
outside the evidence root. A crafted evidence directory containing, e.g., a
`screenshot.png` that is actually a symlink to an arbitrary file elsewhere on
disk would have that file's real content served through
`/api/media/<handle>/screenshot`.

This was undetectable on the Windows development machine this repository's
Batches 1-8 and the entry-gate audit were built on (creating a file symlink
there requires a privilege this account lacks - confirmed `EPERM`), which is
exactly why the entry-gate report (§35) carried it forward as an untested
risk rather than a resolved one. A new regression test
(`tests/unit/viewerEvidenceServer.test.ts`, "a media filename that is itself
a symlink/junction...") creates such a symlink and asserts the linked
content is never served; it no-ops (with an explicit `EPERM`/`ENOSYS`
assertion) where symlink creation isn't permitted, and ran for real on the
Linux CI matrix job, where it caught the vulnerability on the first CI run
of the un-fixed candidate.

**Fix**: `checkExists()` now uses `fs.lstat()` and rejects any entry that
isn't `isFile()` - a symlink's `lstat().isFile()` is `false`, so the media
route now refuses to serve through a symlinked filename at all, closing the
escape without weakening any legitimate behavior. Verified: the regression
test passed on the Linux and macOS matrix runners in the corrected candidate
CI run (see §13); Windows still no-ops on this specific test (symlink
creation unsupported for this account) but the fix itself is
platform-agnostic (`lstat` behaves identically everywhere) and the
Windows-specific traversal/absolute-path tests in the same file continue to
pass.

### 10.8 CORS/origin audit

No `Access-Control-Allow-Origin` (or any other CORS) header is set anywhere

site. The viewer relies entirely on the browser's same-origin policy against

### 10.9 Security headers

`httpServer.ts` sets `content-type` and `cache-control: no-store` on every
dynamic response, and `content-type`/`content-length`/`cache-control` on
media/asset responses, but sets no `X-Content-Type-Options`,
`Content-Security-Policy`, or frame-embedding header. Given this is a
strictly loopback-only server serving only its own built assets (no
third-party content, no user-supplied HTML rendering, no cross-origin
exposure per §10.8), this is a low-risk gap, not an exploitable one.
**Deferred, non-blocking**: adding `X-Content-Type-Options: nosniff` (and
possibly a same-origin-only CSP) would be a reasonable focused addition for
a future hardening pass, but is not required for this stage's PASS and was
not added here to keep this stage's change surface narrow. `SECURITY_HEADER_AUDIT`:
justified current state (no critical/high gap; low-risk item recorded for
follow-up).
