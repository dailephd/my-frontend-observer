## 4. Original isolated failure reproduction

After `npm run build` (exit 0), this command ran against the unchanged test:

`npx vitest run --config vitest.browser.config.ts tests/browser/pwaHardening.test.ts -t "HARD GATE"`

1. Exit code: 1
2. Result: 1 failed, 6 skipped
3. Failure step: `await page.reload()` right after `server.close()`
4. Failure message: `page.reload: net::ERR_CONNECTION_REFUSED`
5. Shell reload failed: yes. The page was not served by a service worker.
6. Evidence-unavailable assertion reached: no. The test failed before it.

A diagnostic outside the repository (scratchpad only, not committed) repeated
the original steps and recorded service-worker and cache state at the moment the
original test shut the server down. The result was the same with the historical
fixed profile and with a fresh temporary profile:

1. Registration present: true
2. Worker state: `installing` = true, `active` = null
3. `navigator.serviceWorker.controller`: null
4. Cache Storage: one `workbox-precache-v2-<origin>/` cache with 5 entries, so
   the precache was still being filled
5. Reload after close: `net::ERR_CONNECTION_REFUSED`

So service-worker control and a complete shell cache were both absent at the
shutdown boundary.

## 5. Root cause

Two faults combined.

1. The wait condition was wrong. The old test waited for
   `(await navigator.serviceWorker.getRegistration())?.active !== undefined`.
   `registration.active` is `null`, not `undefined`, while a worker is still
   installing. The condition was therefore true as soon as any registration
   existed. It never proved activation, control, or a filled precache.
2. The test relied on shared state. In normal file order, earlier tests in the
   same describe had already used the same server origin and the same
   persistent context. By the time the hard gate ran, the worker was active and
   controlling that origin, so the weak wait did not matter.

When selected alone, the viewer server starts on a new random port (`port: 0`).
That is a new origin with no worker. The fixed profile's older registrations
belong to other origins and do not help. The page was still uncontrolled when
the server closed, so the reload went to the network and failed.

Classification stays `TEST_DEFECT`. `PRODUCT_CHANGE_REQUIRED = false`.

## 6. Previous shared-state topology

In the first describe block, `beforeAll` created and shared:

1. one evidence root from `mkdtemp`
2. one viewer server
3. one persistent Chromium context launched from the fixed profile
   `.my-dev-kit-workflow/v0.8/batch-08/pwa-profile`

The hard gate was the fourth `it()` in that block. The three earlier tests
registered the worker, fetched the manifest, and warmed the cache on the same
origin. The fixed profile also kept service-worker and cache data between local
runs. That block's `afterAll` never closed its server. Only the hard gate's
mid-test `server.close()` shut it down.

## 7. New hard-gate resource ownership

The hard gate now lives in its own describe block:
`PWA server-down safety - self-contained hard-gate experiment`. It has no
`beforeAll` and uses no describe-level variables. Inside the test it creates and
owns:

1. an evidence root:
   `mkdtemp(path.join(tmpdir(), 'my-frontend-observer-pwa-hard-gate-evidence-'))`
2. the fixture, through the existing helpers `writeManyRegionsOneTargetFixture`
   and `persistAnnotationUnder`. These are now wrapped by a local
   `writePwaFixture` helper that both describe blocks use. The real annotation
   is kept so the annotation view and media routes are part of the cache
   boundary.
3. a dedicated viewer server from `startViewer` on port 0
4. a persistent profile:
   `mkdtemp(path.join(tmpdir(), 'my-frontend-observer-pwa-hard-gate-profile-'))`
5. a `BrowserContext` from
   `chromium.launchPersistentContext(profileRoot, { headless: true })`
6. a fresh page

The test name is unchanged, so `-t "HARD GATE"` still selects it.

## 8. Fresh-profile design

1. The hard gate uses its own temporary profile and context. It never shares
   one with any other test.
2. The first describe block, which keeps the focused registration, manifest,
   and `/api/` cache tests, now creates its own temporary profile
   (`my-frontend-observer-pwa-profile-*`) in `beforeAll` and deletes it in
   `afterAll`.
3. That `afterAll` now also closes its viewer server, since the hard gate no
   longer closes it.
4. The constant for `.my-dev-kit-workflow/v0.8/batch-08/pwa-profile` was

5. Profile and evidence removal uses
   `rm(dir, { recursive: true, force: true, maxRetries: 5, retryDelay: 200 })`,
   because Chromium can briefly hold profile files after close on Windows.

## 9. Service-worker registration proof

After the first navigation, the test evaluates `navigator.serviceWorker.ready`
in the real page and requires:

1. `registration.active !== null` is true
2. `registration.scope` equals `<viewer origin>/`

`ready` only resolves when a worker is active, so there is no fixed sleep.

Observed: `serviceWorkerActive = true`.

## 10. Current-client control proof

Control is checked on its own, apart from activation:

1. The test reads `navigator.serviceWorker.controller !== null`.
2. If it is null, the page reloads while the server is still live.
3. The test then waits (bounded at 10 seconds) for
   `navigator.serviceWorker.controller !== null`.
4. It requires `controller.scriptURL` to equal `<viewer origin>/sw.js`.

Observed: `controlledOnFirstLoad = true` and `clientControlled = true`. The
generated worker calls `self.skipWaiting()` and `clientsClaim()`, so once
activation finishes it takes control of the first page. The reload branch
stays in place for any platform where control arrives later.

## 11. App-shell cache proof

The test reads every Cache Storage entry from the page before shutdown. It
requires:

1. at least one cache whose name starts with `workbox-precache`
2. cached pathnames that include `/index.html`, `/registerSW.js`, and
   `/manifest.webmanifest`
3. a cached `/index.html` (matched with `ignoreSearch`, because Workbox adds
   `__WB_REVISION__`) whose body contains `<div id="root"></div>`
4. that the module entry script named inside that cached `index.html` matches
   `/assets/*.js` and is itself in the cache

Why this is stable: the generated `sw.js` precaches `index.html`,
`registerSW.js`, and `manifest.webmanifest` under fixed names, and serves
navigations with `createHandlerBoundToURL("index.html")`. Only the Vite asset
names are hashed. The test never hardcodes a hash. It reads the entry script
name from the cached shell, so the check stays valid across rebuilds.

Observed: 7 cached entries (index, registerSW, manifest, two icons, one JS
bundle, one CSS bundle).

## 12. API cache-exclusion proof

From the controlled page, the hard gate first fetches `/api/index`, the
annotation view route, and the annotation overlay media route. It requires each
to return `200` with `cache-control: no-store`. It then counts cached requests
whose pathname starts with `/api/` across every cache.

Observed: `apiCacheEntryCount = 0`.

The separate focused test `never caches /api/ responses at the service-worker
cache-storage layer` was kept. The hard gate does not depend on it.

## 13. Live evidence proof

Before shutdown the test:

1. waits for the first `.evidence-list__item`
2. requires it to be visible
3. requires the `.evidence-list` text to contain the fixture candidate id
   `many-regions-candidate` (read from the fixture helper's return value, not
   hardcoded)
4. makes a direct Node-side `fetch` to `/api/index` (5 second timeout) and
   requires HTTP 200 with a body that contains the same candidate id

## 14. Server-down proof

After `await server.close()` the test makes a direct Node-side `fetch` to the
same `/api/index` URL with a 5 second timeout. A Node request cannot be
intercepted by the page's service worker, so this tests the origin server alone.
The test requires the request to fail. If it gets any HTTP response, the test
fails with that status in the message.

The page was not navigated away. The controlled page and worker stayed in place.

## 15. Offline reload proof

Only after the checks in sections 9 to 14 pass does the test call
`page.reload()`. It then requires:

1. `h1, header` to render within 10 seconds, so the shell was served from the
   precache
2. `navigator.serviceWorker.controller !== null` after the reload

## 16. Stale-evidence safety proof

After the offline reload the test requires:

1. `.evidence-list__error` to appear
2. body text to contain `Evidence index unavailable`
3. body text not to contain the previously visible candidate id
4. zero `.evidence-list__item` elements

These assertions are unchanged from the original or stricter. None were
weakened.

## 17. Cleanup proof

Cleanup runs in `finally` in a fixed order: close the context, close the server
unless it was already closed on purpose, remove the evidence root, remove the
profile. Each step runs even if an earlier step fails. Errors are collected.

1. If the experiment failed, cleanup errors are logged with `console.error` and
   the original assertion error is what the test reports.
2. If the experiment passed but cleanup failed, the test fails with every
   cleanup error listed.
3. After cleanup, the test requires that neither the evidence root nor the
   profile directory exists.

A leak audit counted `my-frontend-observer-pwa-*` and
`my-frontend-observer-b8-pwa*` directories under the OS temp directory before
and after each run. All counts were 0. That covers the hard gate's profile and
evidence root and the first describe block's temporary profile and evidence
root.

Not executed: the failure-path cleanup (steps 1 and 2 above) was not triggered
on purpose. It is supported by code inspection only.
