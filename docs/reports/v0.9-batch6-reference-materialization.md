## 4. Materializable intent boundary

1. Only confirmed `reference-region` (`create` or `refine`) and confirmed
   `reference-requirement` items can be materialized.
2. `referenceMaterializationBlockReason` in the new application service is
   the single server rule:
   1. uninterpreted items are refused;
   2. candidate items are refused;
   3. `inspect` and `asset-sensitive` are refused as informational intent;
   4. runtime `change` intent is refused as not external-reference intent.
3. Only the explicitly selected item ids are used. Unselected items never
   contribute, even when they are confirmed.
4. Selection is atomic. An empty, oversized (more than 100), duplicate, or
   unknown selection, or any blocked item, rejects the whole request before
   any write.
5. The annotation must be saved. The API takes a saved annotation handle only,
   and the UI disables materialization while the draft is unsaved or dirty.

## 5. Source reference validation

The service `materializeVisualAnnotationReference` checks, in order:

1. The annotation passes the canonical `isValidVisualAnnotationArtifact`.
2. `annotation.source.kind` is `external-reference`. A runtime annotation is
   `invalid-source`.
3. The supplied source passes the canonical
   `isValidExternalReferenceArtifact`.
4. The source exactly matches the annotation source identity:
   `referenceId`, `referenceRequestId`, schema version, lifecycle, image owner
   id, image SHA-256, and coordinate width and height. For an approved source
   the image fields come from `sourceReference.image`. A mismatch is
   `source-mismatch`.
5. The supplied `sourceReferenceRoot` is read through the canonical
   `readExternalReferenceArtifact` and must hold the same `referenceId`.
   This keeps canonical supersession tied to the verified source.

## 6. Source image resolution and verification

1. The route never builds an image path from browser data or from the
   annotation's image owner id.
2. The route reads image bytes only through the existing safe
   `resolveMedia` boundary:
   1. `image` role for an imported source;
   2. `source-image` role for an approved source (the owning imported image).
3. The source artifact root comes from the source's own viewer handle through
   `decodeArtifactHandle` and `resolveContainedDir`.
4. The service recomputes SHA-256 over the supplied bytes and requires it to
   equal the source image SHA-256.
5. The bytes are passed unchanged to `importExternalReference`. Nothing is
   transcoded, recompressed, or rasterized. Annotation marks are never baked
   into the image.

## 7. Region composition

1. Final regions start from a copy of `sourceReference.regions ?? []`. The
   source array and its region objects are never mutated.
2. Selected refinements are applied first, in place.
3. Selected creates are then appended in selection order.
4. The final set is validated with the canonical
   `isValidReferenceRegions(finalRegions, image.width, image.height)`. A
   failure is `invalid-materialized-reference` and nothing is written.

## 8. Region create behavior

1. The confirmed `intent.region` is used exactly: id casing and rectangle are
   kept, and no geometry is inferred from the mark.
2. A create id that case-insensitively matches an existing source region is
   rejected.
3. Two selected creates with case-insensitively equal ids are rejected.
4. Nothing is renamed.

## 9. Region refine behavior

1. A refine must target a region that exists in the selected source
   reference. Ids match case-insensitively, as canonical region ids do.
2. The refined region keeps its source id spelling and its position. Only the
   rectangle changes. Unrelated regions keep their order and geometry.
3. Two selected refinements of the same source region are rejected. Item
   order never chooses a winner.
4. Create then refine of the same new region in one request is rejected,
   because the refine target is not a source region.

## 10. Requirement composition

1. Requirements are composed after regions, so a selected requirement may use
   a region created in the same request.
2. Each selected `intent.requirement` is validated with the canonical
   `isValidRawReferenceRequirement` and is not reinterpreted.
3. A requirement that references a region that is not in the final set (for
   example an unselected create) is rejected by the canonical
   `isValidReferenceRequirements`.
4. A selected `region-relationship` requirement must hold for the final
   geometry. The service checks it through the canonical
   `deriveReferenceRequirementExpectation`. A contradicted relationship is
   `invalid-materialized-reference`. This was needed because
   `importExternalReference` validates relationship subjects structurally but
   not against geometry.
5. `region-measurement` requirements persist only the raw subject and
   tolerance. No measured value is stored.
6. Duplicates and conflicts are left to the canonical
   `buildReferenceRequirement` and `isValidReferenceRequirements`. Nothing is
   silently dropped.

## 15. Materialization API

1. Route: `POST /api/annotations/:handle/materialize-reference`, in
   `src/viewerServer/httpServer.ts`. The use case lives in the new
   `src/viewerServer/annotationReferenceMaterialization.ts` so the HTTP layer
   stays thin.
2. It uses the shared Prompt 2/5 gate `readAuthoringJsonRequest` (Host,
   Origin, token, JSON content type, content encoding, body limit) and the
   shared session write queue `runSerializedAuthoringWrite`. No second parser
   or queue exists.
3. The body is exactly `{ itemIds }`. The `itemIds` rule is now one shared
   helper, `parseAuthoringItemIds` in `annotationAuthoring.ts`: a non-empty
   array of at most 100 unique non-empty strings. The promotion parser uses
   the same helper, with identical behavior and messages. Unknown fields
   return 400.
4. Resolution:
   1. `getAnnotationView` resolves the annotation and its exact source handle.
   2. The source must be `available` with family
      `external-reference-imported` or `external-reference-approved`.
   3. `loadArtifactByHandle` loads the source artifact.
   4. Image bytes and the source root are resolved as in section 6.
   5. The canonical service is called once with `referenceOutputLocation()`
      and `cwd` set to the authoring project root.
5. Success returns 201 with exactly `ok`, `referenceId`, `referenceRequestId`,
   `handle` (`external-reference-imported:references%2F<referenceId>`),
   `lifecycle: 'imported'`, `supersedesReferenceId`, `regionCount`,
   `requirementCount`, and `approvalRequired: true`. It contains no paths, no
   project root, and no token.
6. Failure status mapping:
   1. 400: malformed handle, invalid JSON, or invalid body shape.
   2. 403: authoring or security failure, including a read-only viewer.
   3. 404: unknown annotation, source reference unavailable, or source image
      unavailable.
   4. 409: handle is not a visual annotation, runtime annotation, invalid
      source, or source mismatch.
   5. 413: body too large.
   6. 415: wrong content type or content encoding.
   7. 422: unsupported or unconfirmed selection, invalid region or requirement
      composition, stale relationship, or create/refine conflict.
   8. 500: image read failure or persistence failure.
   9. 405 with `Allow: POST` for GET and HEAD on the route. PUT, PATCH, and
      DELETE keep the existing global 405.
7. `VIEWER_PROTOCOL_VERSION` is `1.3.0`. The allowed POST surface is exactly
   `POST /api/annotations`, `POST /api/annotations/:handle/promote-contract`,
   and `POST /api/annotations/:handle/materialize-reference`.
8. `materializeVisualAnnotationReference` and its options, result, and failure
   code types are exported from `src/index.ts`.
