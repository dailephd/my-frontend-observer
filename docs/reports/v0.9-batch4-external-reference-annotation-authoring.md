## 11. Region create candidate

1. Available only for a selected rectangle, with a "Proposed region ID" input
   (`maxLength=64`) and a hint about the allowed characters.
2. The id is never rewritten, lowercased, or replaced.
3. Blocked when:
   1. the id is empty or does not match `^[A-Za-z0-9_-]{1,64}$`;
   2. it duplicates a source region (case-insensitive);
   3. it duplicates another draft create (case-insensitive);
   4. source regions plus other distinct draft creates already reach 20
      (`MAX_REFERENCE_REGIONS`, mirrored).
4. The candidate is
   `{ kind: 'reference-region', mode: 'create', region: { id, rectangle } }`,
   using the exact mark geometry.
5. The preview renders a dashed candidate rectangle labeled
   "candidate new <id> (<state>)".

## 12. Region refine candidate

1. Requires a selected rectangle and a selected existing region. The user
   clicks "Refine selected region <id>".
2. The candidate is `mode: 'refine'` with the same region id and the mark
   geometry. The item is also explicitly associated with that region.
3. The preview shows the original source rectangle and the candidate
   replacement, each with its own distinct class. The source region keeps
   rendering with its original geometry.
4. A summary line reads "Existing source regions: N · Candidate creates: N ·
   Candidate refinements: N" and is marked as not the final region set.

## 14. Candidate reference requirements

1. Categories are exactly `requested`, `expected-dependent`, `protected`, and
   `preserved`. `expected-dependent` requires `required` or `permitted`. For
   other categories the mode is absent, even if one was chosen earlier.
2. Subjects:
   1. `region-property` takes an existing or draft-proposed region and one of
      the 8 canonical properties. A tolerance is required.
   2. `region-relationship` takes only a canonical server relationship,
      selected by index. No tolerance is allowed. Candidate-created regions
      never appear, because they have no derived relationships.
   3. `region-measurement` takes two distinct known regions and one of the 6
      canonical measurements. A tolerance is required. No measured value is
      ever computed or stored.
3. Tolerance kinds are `exact`, `absolute-reference-px` (labeled
   "reference-image pixels"), and `percent`. Amounts must be finite and
   between 0 and 100.
4. "Set candidate requirement" is disabled with a visible reason until the
   form is complete. It sets
   `candidate { kind: 'reference-requirement', requirement }` with the
   canonical `RawReferenceRequirement` shape.
5. The panel lists "Candidate annotation region proposals" and "Candidate
   annotation requirements" separately from the source regions and
   requirements shown by the unchanged reference inspector.

4. Confirmation was proven in the browser for all four families:

## 16. Confirmation invalidation

1. Every reference draft edit passes through `applyReferenceItemEdit`. A
   rectangle's region intent is first synchronized to the rectangle geometry.
2. If the item was confirmed and its meaning changed, it becomes a candidate
   without `confirmedAt`. Meaning covers the mark, the association, and the
   intent.
3. Setting a new intent (region id or mode, requirement fields, tolerance,
   asset region) always produces a candidate.
4. Browser-verified:
   1. Moving a confirmed candidate region synchronizes its rectangle, drops it
      to candidate, and a later reconfirmation gets a new `confirmedAt`.
   2. Changing a confirmed requirement's tolerance requires reconfirmation.
   3. Changing a confirmed item's association requires reconfirmation.
5. Unit-verified: note text edits and asset-region changes also invalidate,
   and a no-op edit keeps confirmation.
