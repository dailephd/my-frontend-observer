## v0.6 bounded-context precedent

`projectBoundedAgentContext` already tiers v0.5 contract-clause targets into required/permitted/context sets, allocates them into `MAX_RUNTIME_TARGETS` capacity with required-first priority, derives `omissions`/`truncations` from what got dropped, and computes `adequacy` purely from those two collections' `required` flags — this exact machinery, not a redesign, is what Prompt 7's fidelity input feeds into.

## Chosen integration owner

`projectBoundedAgentContext` itself, extended with one new optional input (`fidelity?: ReferenceCandidateFidelityEvaluation`, `fidelityRequired?: boolean`) — not a separate `VisualAgentContext`/`VisualPromptPacket`/`ReferencePromptBuilder`, and not a pure post-hoc "attach" step in the shape `attachRuntimeStaticCorrelations` uses. The attach-step shape was considered and rejected: fidelity-relevant runtime targets must compete fairly for `MAX_RUNTIME_TARGETS` capacity and receive full `BoundedRuntimeTargetProjection` treatment (geometry/visibility/overflow/scrollOwner/screenshotRef) through the exact existing per-target assembly code, which an attach-only step run after target allocation has already finished could never produce. A new pure sibling module, `domain/referenceFidelityProjection.ts` (`projectReferenceFidelity`), derives the bounded/prioritized fidelity content plus the target-id/omission/truncation contributions that `projectBoundedAgentContext` folds into its own existing pipeline before allocation, capping, and adequacy computation run.

## Selection policy

Only non-`pass` Prompt 6 requirement results are ever candidates for `mismatches` — passing requirements are never dumped by default (behavior D). Each candidate is classified into a tier by category/mode, reusing `boundedAgentContextProjection.ts#clauseTier`'s exact rule (duplicated as `fidelityRequirementTier`, not imported, per the established per-module small-helper convention): `protected`/`preserved` → `required`; `expected-dependent`/`'required'` → `required`; `expected-dependent`/`'permitted'` and `requested` → `optional`. Passing `protected`/`preserved` results are surfaced separately as `protectedContext` (disjoint from `mismatches` — a *failing* protected/preserved requirement already appears in `mismatches` at the highest priority, never duplicated).

## Priority policy

1. `fail` + `required` tier
2. `unavailable` + `required` tier
3. any other non-`pass` (`optional`-tier) result

Within one priority class, Prompt 6's own authored requirement order is preserved (a stable sort by rank only). The reported `mismatches` array is in priority order (highest first) — verified this is genuinely priority-first, not restored to authored order, by a dedicated test that caught and fixed an initial implementation bug (see Tooling incidents).

## Cap values

`MAX_FIDELITY_MISMATCHES = 15` and `MAX_FIDELITY_PROTECTED_CONTEXT = 10` (reusing `MAX_RELATIONSHIP_EVIDENCE_PER_TARGET`'s value) — both judgment-call bounds in the same spirit as v0.6 Batch 1's own frozen caps (no measured fixture corpus exists yet for either concept, matching that section's own documented rationale).

## Omission/truncation behavior

Reuses `OmissionRecord`/`TruncationRecord` wholesale — no second reporting model. Exceeding `MAX_FIDELITY_MISMATCHES` records `{subject: 'fidelity-mismatches', limit, actualCount, required}` plus one `{subject: 'fidelity-mismatch:<requirementId>', reason: 'required-evidence-lost-by-bound', required: true}` omission per dropped required-tier mismatch. Exceeding `MAX_FIDELITY_PROTECTED_CONTEXT` records a truncation with `required: false` always (confirmatory/passing context is never "required loss"). These records are prepended into `projectBoundedAgentContext`'s own `omissions`/`truncations` arrays before its existing `capOmissions`/`capTruncations` aggregate-cap calls and its existing adequacy computation run — fidelity loss participates in the exact same `anyRequiredLoss`/`anyOptionalLoss` rule every other evidence source already uses, never a separate adequacy code path.

## Adequacy behavior

A `not-evaluated` fidelity always records an explicit omission (`{subject: 'fidelity', reason: 'unsupported-or-unavailable', required, detail}`), where `required` defaults to `true` — supplying a fidelity evaluation to be projected at all is itself the signal that the task depends on it, mirroring `CorrelationTargetInput.required`'s existing v0.6 convention. A `required: true` fidelity omission prevents `adequacy.state` from remaining `'adequate'` (verified: it becomes `'partial'` in the tested scenario, since v0.6's own inadequate-threshold is scoped to runtime-target unavailability specifically — an honest, non-`'adequate'` state either way, never falsely `'adequate'`). A `required: false` omission (`fidelityRequired: false`) never degrades adequacy past `'partial'`, matching v0.6's own pre-existing "optional-only loss never means inadequate" rule exactly — unchanged, not redefined. A `pass` fidelity result contributes no omissions/truncations and never degrades adequacy (verified by a dedicated test).
