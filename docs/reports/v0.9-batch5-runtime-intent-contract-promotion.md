## 5. Move mappings

Move requires an explicit `runtime-target` association.

1. `right` maps to `property-increases x`.
2. `left` maps to `property-decreases x`.
3. `down` maps to `property-increases y`.
4. `up` maps to `property-decreases y`.

`minimumDeltaPx` is never set. Arrow direction and drawing position never
choose the direction. This is browser-verified: an arrow drawn pointing right
stays `uninterpreted`, and an explicit "move left" gives
`property-decreases header.x`.

## 6. Resize mappings

Resize requires an explicit `runtime-target` association.

1. `wider` maps to `property-increases width`.
2. `narrower` maps to `property-decreases width`.
3. `taller` maps to `property-increases height`.
4. `shorter` maps to `property-decreases height`.

`minimumDeltaPx` is never set.

## 7. Preserve mappings

1. With a `runtime-target` association, the user picks one property (`x`,
   `y`, `width`, `height`) and a contract tolerance (`exact`, `absolute-px`,
   or `percent`, amount between 0 and 100). The result is
   `property-unchanged-within-tolerance`.
2. `absolute-px` is labeled "runtime CSS pixels". It is kept distinct from
   the reference vocabulary's `absolute-reference-px`.
3. With a `runtime-relationship` association, the result is
   `relationship-unchanged` with the association's `relationshipKind`, and
   with `subjectTarget` and `relatedTarget` only when present. Page-level
   relationships get no invented targets.
4. No preserve UI exists for visibility, clipping, scroll, document width,
   bounds, fit, overlap, or relative width.

## 11. Confirmation invalidation

1. `useRuntimeAnnotationDraft` now routes every edit through
   `applyRuntimeItemEdit`: reconcile, then withdraw a changed confirmation.
   Edits here are mark moves, note text, association set or clear, and new
   intents.
2. Reconciliation:
   1. A target change retargets `primitive.target`.
   2. A relationship change rewrites the `relationship-unchanged` primitive.
   3. An incompatible association, or clearing it, sets the change
      interpretation back to `uninterpreted`. It is never coerced.
3. A confirmed item whose mark, association, or intent changes goes back to
   `candidate` without `confirmedAt`. A no-op edit keeps confirmation.
4. Browser-verified: changing a confirmed move from `header` to `footer`
   gives `primitive.target: footer` and state candidate. Reconfirmation
   works. Moving the mark again gives candidate.

## 12. Promotable-item rules

An item is promotable only when all of these hold:

1. It is `confirmed`.
2. `intent.kind` is `change`.
3. The operation is `move`, `resize`, or `preserve`.
4. A valid `contractPrimitive` is present, checked with the existing
   `isValidContractPrimitive`.
5. A runtime association is present.
6. The primitive matches both the association and the operation:
   1. `move` uses `x` or `y`; `resize` uses `width` or `height`.
   2. Both use increases or decreases on the associated target, with no
      `minimumDeltaPx`.
   3. Preserve on a target uses a property primitive on that target.
   4. Preserve on a relationship uses exactly that relationship.

Uninterpreted, candidate, inspect, remove, missing-primitive, unbound, and
mismatched items are not promotable. The viewer's `runtimePromotionStatus`
drives presentation only. The server repeats every check.

## 13. Annotation-to-contract application service

New `src/application/visualAnnotationContractPromotionService.ts`,
`promoteVisualAnnotationContract(options)`:

1. Validates the annotation with the canonical `isValidVisualAnnotationArtifact`.
2. Requires a `runtime-observation` source. Anything else is
   `unsupported-source`.
3. Requires the supplied observation to exactly match the source.
   Otherwise it is `source-mismatch`. The fields compared are
   `observationId`, `requestId`, schema version, screenshot recorded and path
   equal, and viewport width and height.
4. Rejects the whole promotion (`invalid-selection`, nothing written) for any
   of these: empty, more than 100, duplicate, unknown, or any non-promotable
   selected item. It never writes a partial contract.
5. Clause order follows `selectedItemIds` exactly.
6. Persists exactly once through `persistPerChangeContract`, which is
   unit-verified with a spy.
7. The result is a discriminated union with a failure `code` and `reason`,
   consistent with the other application-service result shapes.

## 18. Promotion API

1. `POST /api/annotations/:handle/promote-contract`. `GET` and `HEAD` on it
   return 405 `Allow: POST`.
2. `POST /api/annotations/:handle/materialize-reference` still returns 405.
   PUT, PATCH, and DELETE stay unsupported.
3. The route uses one shared gate, `readAuthoringJsonRequest`, extracted from
   the Prompt 2 save handler and now used by both routes. It covers authoring
   enabled, Host, Origin, token, JSON content type, identity encoding, the
   262144-byte limit, and JSON parsing. There is no second token, session, or
   parser.
4. The body is closed to `{ itemIds, activateForCheck }`:
   1. `itemIds` is non-empty, at most 100, non-empty strings, unique.
   2. `activateForCheck` is a required boolean.
   3. Unknown fields give 400.
5. The new module `src/viewerServer/annotationContractPromotion.ts` owns the
   route use case. It was added so the route stays thin.
   1. It resolves the annotation with `getAnnotationView`, which uses
      `loadArtifactByHandle`.
   2. It requires the runtime source. Reference annotations give 409.
   3. It resolves the exact source through the Prompt 2 annotation source
      view plus `loadArtifactByHandle`. A missing source gives 404.
   4. It resolves the configured baseline, calls
      `promoteVisualAnnotationContract` once with `contractOutputLocation()`
      and the project root, and then optionally activates.
   5. It runs through the session's single authoring write queue. That queue
      is the Prompt 2 queue exposed as `runSerializedAuthoringWrite`, so
      promotion never interleaves with saves.
6. Status mapping:
   1. 201: success.
   2. 400: request shape or malformed handle.
   3. 403: security gate.
   4. 404: unknown annotation or missing source.
   5. 409: not an annotation, a reference annotation, invalid project config,
      invalid configured baseline, or source mismatch.
   6. 413: body too large. 415: media type or encoding.
   7. 422: non-promotable selection.
   8. 500: persistence failure.
7. The 201 body is exactly
   `{ ok, contractId, contractRequestId, handle, clauseCount, activation }`.
   The handle is `change-contract:contracts%2F<contractId>`. No paths are
   returned.
8. `VIEWER_PROTOCOL_VERSION` is now `1.2.0`. The Prompt 2 security test was
   updated for the new version and for the now-real promote route. Its 405
   list still includes `materialize-reference`.

## 21. Temporary-directory discovery hardening

1. Implemented. `src/viewerServer/evidence/discovery.ts` never descends into a
   directory whose basename starts with `.tmp-`, at any depth. The prefix is
   the new exported `WRITER_TEMP_DIRECTORY_PREFIX`. Every canonical writer in
   `src/artifacts/` uses it for its sibling temp directory.
2. The skipped directory is not read, classified, returned, or deleted.
3. Final artifact discovery is unchanged:
   1. A normal directory is discovered.
   2. The same artifact renamed from `.tmp-abc` to `final-abc` is discovered.
   3. A name like `x.tmp-y` is still discovered.
   4. All existing discovery tests pass.
4. Structural test (`tests/unit/evidenceDiscoveryTempDirectories.test.ts`):
   manifests under `.tmp-top`, `annotations/.tmp-abc`, `contracts/.tmp-def`,
   and `references/nested/.tmp-ghi` are not discovered. This test failed
   before the change and passes after it.
5. Concurrency regression: 25 atomic annotation saves while
   `buildEvidenceIndexMetadata` runs continuously. Before committing, a
   heavier ad-hoc probe also ran against the unfixed code: 4 concurrent
   refresh loops and 60 saves of 40 items each. The probe file was deleted.
   Neither reproduced `EPERM` in-process, before or after the change.
6. Conclusion: the Windows writer/discovery race is structurally mitigated.
   Discovery can no longer hold handles inside a writer's temp directory. It
   is not claimed as proven fixed, because no deterministic reproduction was
   available.
7. The concurrency test remains as a regression guard. The writers were not
   changed and no retry loop was added.
