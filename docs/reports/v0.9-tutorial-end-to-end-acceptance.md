## 8. Scenario content-quality audit

Every step was read and judged against the questions the task sets: whether
the narration explains why an operation exists, whether it draws the
distinction that matters, whether the step does real product work, and whether
it is materially more useful than naming the control being clicked.

The audit found six genuine defects. All six were corrected in this stage and
all four scenarios were then rerun from clean targets. The corrections
stayed inside scenario narration, pauses, screenshot requests, callouts and
scenario step sequence. No product behavior was changed.

### 8.1 Narration that contradicted the evidence (scenario 4)

The second requirement in `04-reference-materialization` was narrated as being
about the footer, and the tutorial's whole point is that the unselected
requirement is a real, confirmed, correct requirement left out of the
revision. The saved evidence from the Prompt 2 run says otherwise:

```text
{"category":"preserved","subject":{"kind":"region-property","region":"promo-band","property":"height"}}
```

The requirement-region select keeps its previous value, `hero`, and the region
list is the reference's own regions in import order followed by the regions
the draft proposes. Six `ArrowDown` presses from `hero` therefore pass
`sidebar, content, cta, asset, footer` and land on the draft's own
`promo-band`. One press too many selected a different but equally valid
region, so nothing failed and the run passed with narration that was untrue.

Correction: the press count is now five, which lands on `footer`. The step
`req-b-region-6` was removed and the five remaining presses now name the value
each one lands on. The scenario now also asserts the resulting structured
requirement immediately:

```json
{ "type": "text-contains", "expected": "\"region\": \"footer\"" }
{ "type": "text-contains", "expected": "\"property\": \"height\"" }
```

That assertion is the regression guard: the same defect would now fail the run
instead of producing a confident false statement. The final run confirms the
unselected requirement is `preserved footer.height`, and that it did not
materialize.

Note for the record: section 21 of `docs/reports/v0.9-tutorial-integration.md`
describes this item as "the unselected footer requirement". That statement was
inaccurate for the Prompt 2 candidate. It is accurate for the current one.

### 8.2 Narration that was too fast to read (all four scenarios)

No step declared a pause, so each step lasted only as long as its action. In
the Prompt 2 run, `01-annotation-basics` played 4301 characters of narration
in 20.7 seconds, and its opening 40-word subtitle cue was on screen for 256
milliseconds. The structure was valid and the content was good, but nobody
could read it. That is the "near-zero instructional visibility" the timing
audit asks about.

Correction: every step now carries a `pauseAfterMs` sized from its own
narration at 15 characters per second, never below 1.2 seconds. The pause runs
after the action and after any callout is drawn, so it extends both the
subtitle cue and the time a callout stays readable, and it is inside the
step's timeline, so subtitles and manifest stay consistent.
`tests/unit/v09TutorialScenarios.test.ts` now enforces that floor, so
lengthening a narration without lengthening its pause fails a unit test.

### 8.3 A claim the tutorial never demonstrated (scenario 1)

`01-annotation-basics` told the viewer that saving again writes a new
annotation recording which one it revises, and that the original stays
untouched. It then stopped at the revision draft without saving, so the
strongest claim in the tutorial was the one thing it never showed, and there
was no supersession chain in the evidence to verify.

Correction: five steps were added. In the revision draft the point mark, which
was saved with no association, is explicitly associated with `card1` and the
revision is saved. The canonical check in section 17 now verifies a real
two-artifact chain.

### 8.4 View state that made the revision unreadable (scenario 1)

After the reload, the relationship overlay returns, because a view toggle is
page state rather than evidence. The final revision screenshots were covered
in dashed relationship lines.

Correction: one step switches the overlay off again, and its narration uses
the moment to make the point that the annotation came back from disk while the
toggle did not.

### 8.5 Mechanical narration on keyboard steps

Several keypress steps read only "Stepping down." Individually harmless, but a
recording that says "Stepping down" eleven times teaches nothing and makes the
keyboard-driven select changes hard to follow, which is exactly what review
question 8 asks about.

Correction: each press in a run now names the value it lands on, for example
"Inspect.", "Move.", "Resize.", "Remove.", "Preserve.", and the first press of
each run explains what is being chosen and why. The vocabulary order is now
visible in the recording instead of implied.

### 8.6 Narration that did not name what was chosen

Two steps described a mark's position rather than the association actually
made. In scenario 2 a line is drawn across the call-to-action band and then
bound to the first derived relationship, which is `header` horizontally
overlapping `navigation`. In scenario 3 the narration said the header "sits
above" the hero while the requirement protects `horizontally-overlapping`.

Correction: both now name the relationship, and scenario 2 turns the mismatch
into the lesson: where a mark is drawn never decides what it is about. Both
scenarios now assert the relationship they narrate.

### 8.7 Judgement on the rest

The remaining narration passes. Short lines such as "Confirmed." appear only
on steps whose meaning was explained immediately before, and the substantive
steps explain purpose rather than naming controls. No step's substance is only
"Click Rectangle" or "Press Confirm".
