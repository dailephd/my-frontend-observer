### 4.2 Local implementation choices

These choices were left open by the frozen plan and this prompt.

1. Every annotation object is a closed shape. Unknown fields are rejected, the
   same way `isValidContractPrimitive` already rejects them. This is how the
   validator rejects mixed forms, such as a candidate with `confirmedAt`, and
   stray fields such as an alias or a viewer URL.
2. A runtime `runtime-relationship` with a pairwise kind needs two non-empty,
   distinct targets. This matches `PairwiseLayoutRelationship`. A page-level
   kind must not carry targets. This matches `PageLevelLayoutRelationship`.
3. A reference source with lifecycle `imported` must have
   `imageOwnerReferenceId` equal to `referenceId`. A reference source with
   lifecycle `approved` must name a different owning reference. This mirrors
   the existing external-reference ownership model.
4. `annotationId` names the artifact directory. The validator requires it to
   be a single safe path segment: no separators, no colon, no NUL, and not
   `.` or `..`. `source.screenshot.path` follows the same bare-filename rule.
5. Invalid content given to the persistence service is refused with the
   existing `invalid-request` diagnostic. No new diagnostic code was added.
6. Batch 1 does not check whether an associated target or region exists in
   another artifact. It does not check `contractPrimitive` against the item's
   association either. Those checks belong to later batches.

## 5. Identity contract

1. The request identity hashes exactly
   `{ source, items, supersedes: supersedesAnnotationId ?? null }`. The hash is
   built by sorting object keys recursively, keeping array order, serializing
   to JSON, and taking the lowercase SHA-256 hex. The module has its own
   private `canonicalize`, which follows the repository convention.
2. Excluded from the request identity: `createdAt`, the output location, cwd,
   project root, alias, viewer port, HTTP handle, temporary directory, overlay
   SHA, and `annotationId`. The function accepts none of these as inputs.
3. Instance identity is `${annotationRequestId}-${randomBytes(16).toString('hex')}`.
   It is never based on a timestamp.
4. Supersession is carried forward as given. It is part of the request
   identity, and the validator rejects an empty value or a value equal to
   `annotationId`. Batch 1 does not resolve lineage.

## 6. Overlay contract

1. Owned filename: `annotation-overlay.svg`. The manifest `overlay.path` must
   be exactly this value, and `overlay.format` must be `svg`.
2. The root element uses the source dimensions:
   `<svg xmlns="http://www.w3.org/2000/svg" width="W" height="H" viewBox="0 0 W H">`.
   The manifest `overlay.width` and `overlay.height` must equal the source
   coordinate-space dimensions.
3. Determinism:
   1. Output depends only on the source dimensions and the marks, rendered in
      the persisted item order.
   2. Style values are fixed constants.
   3. Numbers are formatted with `String(n)`, and `-0` is written as `0`.
   4. Lines end with `\n`.
   5. The arrowhead is built with `Math.sqrt` vector math, not trigonometry.
   6. Output never depends on interpretation state, item ids, timestamps,
      random values, environment, locale, or the filesystem.
4. Mark mapping:
   1. A point becomes a circle.
   2. A rectangle becomes a rect.
   3. A line becomes a line.
   4. An arrow becomes a line plus a filled polygon arrowhead. A zero-length
      arrow gets no arrowhead.
   5. A note becomes a filled anchor circle plus a text element.
5. The SVG has no image, script, foreignObject, href, marker ids, CSS imports,
   or event handlers. It never embeds the source image.
6. SHA-256 verification:
   1. The service hashes the rendered UTF-8 bytes.
   2. The writer re-renders the overlay and refuses to write if the digest
      differs from `overlay.sha256`.
   3. The reader hashes the bytes on disk and refuses them if the digest does
      not match.
7. Text escaping: note text escapes `&`, `<`, `>`, `"`, and `'`. Characters
   that XML 1.0 does not allow are replaced with U+FFFD in the overlay only.
   The manifest keeps the authored text exactly as written.

## 7. Persistence contract

1. Final directory: `<outputLocation>/<annotationId>/`
2. Temporary directory: `<outputLocation>/.tmp-<annotationId>`
3. Write order:
   1. Validate the artifact.
   2. Render the overlay and verify its digest.
   3. Refuse if the final directory already exists.
   4. Remove this artifact's own stale temporary directory, if one exists.
   5. Create the temporary directory.
   6. Write `annotation-overlay.svg`.
   7. Write `manifest.json`.
4. Atomic rename: the temporary directory is renamed to the final directory in
   one `rename` call.
5. No overwrite: if the final directory already exists, the writer returns
   `artifact-write-failure` and leaves the existing files untouched.
6. Failure cleanup: on any failure after the temporary directory is created,
   the writer removes it and returns `artifact-write-failure`.
7. The writer never reads or copies source observation or reference bytes.
8. The service checks the output location with `normalizeOutputLocation`. It
   uses `getProducerInfo()` and sets `provenance.origin` to `viewer`. It
   writes exactly once.
