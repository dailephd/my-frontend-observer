## Defect and correction

Project-aware `check` validated an immutable baseline before capture, but the candidate capture used only the project configuration. When the baseline carried `requestConfig.scrollScenario` or `requestConfig.explicitState`, the candidate omitted those dimensions and could be classified as incomparable even when rendered evidence had no differences.

After baseline validation, `checkProject` now derives an optional, narrow replay context from the validated baseline artifact and passes only `scrollScenario` and `explicitState` to candidate capture. Current project configuration still owns URL, viewport, semantic targets, and ordinary capture defaults. The canonical request normalization and browser observation path remain responsible for validation and actual scroll execution. Unrelated baseline request fields are not replayed.

`scrollScenario` replay executes the same bounded browser scroll action. `explicitState` replay retains caller-declared identity metadata only; it does not establish theme, application, authentication, cookie, storage, or session state. No state inference or setup was added. Controlled state/session setup remains future v0.12 scope.

## Changed owners and preserved boundaries

The implementation extends `src/application/projectCheckService.ts` and the existing candidate capture path in `src/application/projectWorkflowService.ts`, with unit, workflow, and real-Chromium regression coverage. It does not alter the comparison rules or weaken comparability.

Project config remains schema `1.1.0` and still rejects top-level `scrollScenario` and `explicitState`. Normal `init` and `capture` remain project-config-driven. The machine-facing CLI remains `check <baseline> --json`; no flags were added. Observation schema remains `1.2.0`; comparison schema remains `1.0.0`; check-result schema remains `1.0.0`. Viewer protocol is unchanged. No dependency was added, and package version remains `0.10.0`.
