## 5. Runtime annotation discovery

`viewer/src/hooks/useRuntimeAnnotations.ts` uses only existing APIs.

1. `GET /api/index` gives the candidates: `family === 'visual-annotation'`,
   `supportState === 'supported'`, and
   `relatedIds.sourceObservationId === observationId`. At most 100 candidates
   are checked, and truncation is reported.
2. `GET /api/annotations/:handle/view` confirms each candidate. The pure
   helper `annotationViewBelongsToObservation` requires `source.status`
   `available`, `source.family` `observation`, and `source.handle` equal to
   the selected observation handle.
3. Aliases, relative directories, and labels are never used to join an
   annotation to an observation.

The panel's saved list shows, for each annotation:

1. `annotationId`
2. item count
3. confirmed item count
4. whether it is a revision

No paths are shown. Selecting a saved annotation copies its items into the
in-memory draft. It sets that annotation as the parent handle and keeps every
`annotationItemId`. The persisted artifact is never mutated.

## 6. Shared SVG source-coordinate transform

2. `viewer/src/hooks/useZoomPan.ts` now calls this helper. Its private

3. Annotation drawing and moving (`useAnnotationPointerInteraction.ts`) call

4. A search of `viewer/src` finds exactly one `getScreenCTM()` or

   devicePixelRatio, CSS ratios, or manual aspect-ratio math are used.
5. The source frame is `artifact.requestConfig.viewport` (runtime CSS pixels).
   Coordinates are never rounded, clamped, or scaled. A pointer position
   outside `0..width` by `0..height` is ignored. A gesture keeps its last
   valid in-frame position.

## 7. Interaction modes

1. `AnnotationInteractionMode` is the closed set `select`, `pan`, `point`,
   `rectangle`, `line`, `arrow`, `note`. It is defined in the new pure module
   `viewer/src/annotation/annotationGeometry.ts`.
2. `useAnnotationPointerInteraction` attaches exactly one handler set to the
   SVG at a time:
   1. `pan`: the existing `useZoomPan` pointer handlers only. Target and mark
      pointer input is disabled.
   2. Drawing modes: drawing handlers only. Target rectangles get
      `pointer-events: none`, and marks are not selectable, so drawing over a
      target never selects it and never moves marks.
   3. `select`: target selection, mark selection, and mark drag-to-move. The
      background neither pans nor draws.
3. A drag therefore can never mean both pan and draw.

## 9. Draft lifecycle

`viewer/src/hooks/useRuntimeAnnotationDraft.ts` owns the draft.

1. New annotation: no items, no parent, nothing selected, not dirty.
2. Drawing:
   1. Point and note are created on pointer release at the pointer-down
      source point.
   2. Rectangle, line, and arrow show a dashed preview while dragging and are
      created on release.
   3. Rectangles are direction-normalized. A zero-width or zero-height
      rectangle is not created.
   4. Local choice: a zero-length line or arrow is not created either.
   5. A note is created only when the toolbar note text is 1 to 2000
      characters.
3. New item: `annotation-item-${crypto.randomUUID()}`, no association,
   `interpretation: { state: 'uninterpreted' }`. It is selected on creation
   and marks the draft dirty.
4. Move (select mode): drag a mark past a 3-pixel threshold. It translates
   rigidly by the source delta through the shared transform. A translation
   that would leave the frame is not applied. The id, association, and
   interpretation are unchanged. There are no resize handles.
5. Note edit: a controlled textarea for the selected note changes only
   `mark.text`, bounded at 2000 characters. Saving is disabled while any note
   is empty.
6. Delete draft item removes the item from memory only. No HTTP DELETE is
   sent.
7. Cancel changes restores the loaded persisted items, or an empty draft for a
   new annotation. It also clears transient drawing and any save error.
8. Loaded items keep their persisted interpretation. No interpretation UI
   exists in this batch.

## 13. Save/reload behavior

1. Save runs only when the session is `available`. It POSTs
   `{ sourceHandle, parentAnnotationHandle?, items }` with `content-type` and
   the token header. The browser supplies Origin.
2. On 201, the UI:
   1. Reads the returned handle.
   2. Re-reads the canonical view.
   3. Replaces the draft items with the persisted items.
   4. Sets the parent to the new handle.
   5. Clears dirty.
   6. Shows "Saved annotation <id>".
   7. Refreshes the saved list.
3. On failure (403, 404, 409, 413, 422, 500, or network), the UI shows a
   concise message, keeps the draft, and does not retry. It never falls back
   to a new root annotation.
4. After a browser reload the token is re-acquired and the saved list rebuilt.
   No draft is recovered, because none is stored in the browser.

## 14. Revision behavior

1. After a save, or after selecting a saved annotation, further edits save as
   a child. The new artifact has a fresh `annotationId` and
   `supersedesAnnotationId` pointing to the parent. It then becomes the loaded
   parent.
2. The parent's manifest bytes are unchanged (browser-verified).
3. A stale parent gets 409. The UI shows "Save conflict", keeps the draft,
   sends no second POST, and writes nothing.
