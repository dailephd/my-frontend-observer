## 5. Demo architecture

The demo is a small deterministic HTML, CSS and JavaScript application. No
frontend framework, no second Vite application and no build system was added,
and no dependency was added or upgraded.

The architecture has three separable pieces:

1. An immutable tracked template under `examples/v09-demo/`.
2. A materialization script that copies that template into a caller-provided
   disposable target root.
3. A loopback-only static server that serves one materialized (or explicitly
   pointed-at) demo application on a caller-selected port.

Geometry lives entirely in CSS custom properties keyed on a single
`data-demo-state` attribute. The server freezes the requested state into that
attribute before serving the document. One small classic script owns the only
two differences CSS cannot express honestly: removing an element from the DOM,
and pointing an image at a different local file.

## 8. State model

Nine frozen states, selected deterministically through the URL query parameter
`?state=<state>`:

```text
baseline
move-hero
wider-sidebar
changed-spacing
move-footer
removed-card
changed-asset
multi-change
reference
```

Omitting `?state=` renders `baseline`. An unrecognized state fails closed: the
server answers HTTP 400 with an explicit invalid-state document that names the
rejected value (HTML-escaped) and lists the supported states. The application
itself is never rendered for an invalid state, and no unrelated state is ever
silently substituted.

No state name needed to differ from the task's vocabulary.

## 10. Change-state semantics

Measured against baseline with real Chromium:

1. `move-hero` - hero `x` increases from 325 to 485, exactly +160px. Hero
   width, `y` and height are unchanged, and every other demo target is
   byte-identical to baseline. This is the clean `Move Right` ->
   `property-increases x` example.
2. `wider-sidebar` - sidebar `width` increases from 260 to 400, exactly
   +140px. Sidebar `x`, `y` and height are unchanged, and the header and
   footer do not move. This is the clean `Resize Wider` ->
   `property-increases width` example.
3. `changed-spacing` - the measured horizontal gap between the sidebar's right
   edge and the content region's left edge grows from 24px to 96px. Neither
   region's own width changes, and no demo target changes its `y`. This is a
   relationship and measurement change, not a region change.
4. `move-footer` - footer `y` decreases from 828 to 764, exactly -64px, while
   footer `x`, width and height are unchanged and every other target is
   identical to baseline. The footer lifts off the bottom edge, which is
   deliberately the shape of a real layout regression.
5. `removed-card` - `card-2` is genuinely absent from the document. The
   canonical observation reports `selectionStatus = not-found` and no geometry
   evidence, rather than fabricated geometry. `card-1` and every other target
   are identical to baseline. This demonstrates human intent that v0.9 can
   annotate as a `remove` operation but that the current `ContractPrimitive`
   vocabulary cannot promote into a contract clause.
6. `changed-asset` - the illustration image `src` changes from
   `assets/asset-primary.svg` to `assets/asset-alternate.svg`. Every demo
   target's geometry, including the asset container's, is identical to
   baseline, so an asset-sensitive difference is never conflated with geometry.
7. `multi-change` - five deterministic differences at once: hero `x` 625,
   sidebar width 400, footer `y` 764, `card-2` absent, and the alternate asset.
   This is the state for exercising selected-only contract promotion and
   selected-only reference materialization. It is deliberately not the primary
   simple tutorial state.

## 11. Reference state

  325);
- relationship and measurement: the sidebar-to-content gap is 56px (baseline

- asset-sensitive area: the alternate local illustration;

The page frame stays comparable: header and footer geometry are identical to
baseline, and every demo region is still present. The reference is a design,
not a removal.

## 12. Local asset policy

Every asset is a local file committed beneath `examples/v09-demo/`. There is no
CDN, no Google Fonts, no external image URL, no external API and no
network-dependent icon library. The demo renders correctly offline.

This is enforced two ways. A unit test scans every demo application file and
fails on any `http://` or `https://` reference (excluding the SVG XML
namespace declaration, which is an identifier and never fetched). A real
Chromium test records every network request origin while loading all nine
states and asserts the only origin contacted is the demo's own loopback server.

## 13. Materialization

```powershell
node examples/v09-demo/scripts/prepare.mjs <targetRoot>
```

The target root is required and never defaulted. It is resolved absolutely and
validated before anything is removed. The script refuses:

- a missing, empty or whitespace-only argument;
- a target root containing a null byte;
- a filesystem or drive root;
- any path with fewer than two segments below its root;
- the user's home directory;
- the repository root;
- the immutable demo template, or anything inside it;
- any directory that contains the repository, which a reset would destroy.

Reset semantics are "rematerialize the target root": a rerun destroys and
recreates the target, so it always ends in the same clean state. There is no
separate reset command, matching the task's contract.

A materialized target contains exactly:

```text
<targetRoot>/app/index.html
<targetRoot>/app/styles.css
<targetRoot>/app/state.js
<targetRoot>/app/assets/asset-alternate.svg
<targetRoot>/app/assets/asset-primary.svg
<targetRoot>/app/assets/brand-mark.svg
<targetRoot>/server.mjs
```

That is everything needed to serve the demo without reaching back into the
template or into any generated Observer evidence. The fixed reference PNG is
deliberately not copied: it is not needed to serve the application, and Prompt
2 imports it through canonical Observer commands from its tracked path.

## 14. Source immutability

The tracked template is read-only during materialization. A test takes a
SHA-256 fingerprint of every file under `examples/v09-demo/` before the
materialization suite runs and compares it after a destructive rematerialization
has occurred; the fingerprints must match exactly. A further test asserts that
nothing new appeared beside the template's own directories, and that every file
written during the run lives under the selected target root.

Materialization destroys and recreates only the explicitly selected disposable
target root, and only after every containment and safety check has passed.

No generated `.frontend-observer` evidence exists anywhere in the template, and
a test enforces that.

## 15. Demo server

`examples/v09-demo/scripts/server.mjs` is a small Node HTTP server using only
Node built-ins. No dependency was added.

Behavior:

- binds `127.0.0.1` only; the test reads the bound address back from the OS
  rather than trusting the requested constant;
- serves only the resolved demo application directory;
- resolves every request path inside that directory and fails closed on `..`
  segments, `.` segments, backslashes, null bytes and percent-encoded forms of
  the same;
- serves only a small allowlist of static types (`.html`, `.css`, `.js`,
  `.svg`, `.png`, `.json`); anything else is 404 rather than a guessed type;
- answers only `GET` and `HEAD`; any other method is 405;
- sends `cache-control: no-store` and `x-content-type-options: nosniff`.

Port selection is always the caller's. `4173` appears nowhere in the file, and
a test asserts that. The command line requires `--port` and validates it as an
integer in `1..65535`, rejecting a missing value, a non-integer, `0`, a
negative value and `65536`. The exported `startDemoServer({ port })` additionally
accepts `port: 0` for in-process automation, where the OS assigns an ephemeral
port; this mirrors the repository's existing canonical viewer port contract in
`src/viewerServer/port.ts`, which documents the same allowance for deterministic
test use. A test proves the server listens on exactly the port the caller
selected.

An optional `--app-root <dir>` lets the tracked template be served directly
while editing the demo. A materialized target needs no such flag: the server
resolves `app/` beside itself.

No lab `TutorialTargetContractV1` was frozen or committed. That belongs to
Prompt 2, once the demo, the Observer project bootstrap and the project-aware
viewer can be composed with dynamic loopback ports.

## 17. Reference PNG

`examples/v09-demo/references/v09-reference.png` is a fixed 1440x900 PNG
(55,876 bytes) captured from the demo's `reference` state.

It was produced by `examples/v09-demo/scripts/generate-reference.mjs`, which
serves the `reference` state on loopback and captures it through the
repository's own canonical Chromium observation path (`captureViewportInternal`
from `src/browser/chromiumAdapter.ts`, via the compiled `dist/` module). No
second screenshot engine was added. The script requires a prior `npm run build`
and fails with an explicit message if the compiled modules are missing.

`examples/v09-demo/references/v09-reference.provenance.json` records the source
demo state, the canonical viewport, the image format, how the image was
captured, the exact regeneration command and the intended tutorial use. It is a
plain record beside the asset: it declares no artifact kind and no Observer
schema version, and a test asserts both fields are absent.

The committed PNG is a fixed demo asset. Nothing regenerates it during an
ordinary test run; regeneration is an explicit manual command so an intentional
visual change is reviewed deliberately.

No generated `.frontend-observer/` reference artifacts were committed. Import
and approval of this PNG through canonical Observer commands, inside a
disposable target, belongs to Prompt 2.
