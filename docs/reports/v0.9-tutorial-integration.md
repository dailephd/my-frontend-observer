## 5. v0.4.8 positional pointer-action contract

The released shapes, taken from the validator and the executor:

```json
{
  "type": "pointer-click",
  "locator": { "kind": "test-id", "testId": "runtime-annotation-surface" },
  "position": { "x": 0.33, "y": 0.48 },
  "coordinateSpace": "fraction",
  "timeoutMs": 5000
}
```

```json
{
  "type": "pointer-drag",
  "locator": { "kind": "test-id", "testId": "runtime-annotation-surface" },
  "from": { "x": 0.24, "y": 0.18 },
  "to": { "x": 0.83, "y": 0.36 },
  "coordinateSpace": "fraction",
  "timeoutMs": 5000
}
```

Contract facts that matter for authoring:

- `coordinateSpace` is required and its only accepted value is `"fraction"`.
- Coordinates are fractions of the located element's own bounding box, with
  inclusive bounds `[0, 1]`. Anything outside that fails validation.
- A zero-length `pointer-drag` is rejected by the validator, so a drag always
  expresses a real gesture.
- Execution is real Playwright mouse input: `mouse.move`, `mouse.down`, for a
  drag a `mouse.move` to the end point in a fixed 8 steps
  (`POINTER_DRAG_MOVE_STEPS = 8`), then `mouse.up`. The `mouse.up` runs even
  when the movement throws, so a failed step cannot leave a button held down.
- Both actions wait for the located element to be visible and then read its
  bounding box. They anchor to one element rather than to the page, so a
  scenario still cannot address arbitrary screen coordinates.
- The cursor, click feedback, highlight and callout overlays are the lab's own
  and are unchanged; Observer contributes none of them.

Both names match what the defect diagnosis suggested, but they were taken from
the released package, not assumed.

## 6. Pointer defect reproduction closure

The v0.4.7 blocker was that `drag` resolved two locators and dragged between
their element centres, while Observer drawing needs two freely chosen points
inside one surface. In every drawing mode the viewer deliberately makes target
rectangles pointer-inert, so the only pointer-receiving element covering the
drawing surface was the single screenshot `<image>`, and two locators could not
yield two distinct points of one element.

Before writing any scenario, that exact interaction was reproduced against the
real demo, the real project-aware viewer and the real released v0.4.8 CLI. A
disposable gate scenario drove all five drawing primitives and asserted the
draft item count after each one:

```text
step              action           result   draft item count
rectangle-draw    pointer-drag     passed   0 -> 1
line-draw         pointer-drag     passed   1 -> 2
arrow-draw        pointer-drag     passed   2 -> 3
point-place       pointer-click    passed   3 -> 4
note-place        pointer-click    passed   4 -> 5
```

The run finished `status: passed` with `cleanupErrors: []`, and the captured
screenshot shows five real marks on the observation with the panel reporting
"5 draft items". The marks were created through the viewer's ordinary pointer
event path: `useAnnotationPointerInteraction`'s pointerdown, pointermove and
pointerup handlers on the source-frame SVG.

No Observer workaround was involved. No hidden control, no tutorial-only
endpoint, no direct annotation POST, no `page.evaluate`, no React state
mutation and no synthetic fixture. The gate passed with zero Observer source
changes: the two viewer selectors described in section 14 were added
afterwards, for authoring quality, not to make the gate pass.

One measured detail that shaped every scenario: the drawing SVG's bounding box
maps one-to-one onto the source frame, so a fraction of the element is a
fraction of the captured viewport. That is why the committed coordinates read
as sensible positions on the page.

## 8. Disposable tutorial target architecture

Each run gets a lab-owned run root. The lab passes `<runRoot>/target` to the
prepare command as `{{targetRoot}}`, and prepare builds a complete throwaway

```text
<targetRoot>/demo/                    materialized deterministic demo

<targetRoot>/.frontend-observer/      canonical managed evidence state
```

These are the current canonical Observer paths (`PROJECT_CONFIG_FILENAME` and
`PROJECT_STATE_DIRECTORY`), not a parallel layout. No second project
configuration was invented.

Nothing is ever written under `examples/v09-demo/`. The demo the lab serves is
the materialized copy inside the target root, not the tracked template.

## 9. Dynamic target-contract generation

`examples/v09-demo/scripts/generate-tutorial-target.mjs` writes one contract to
an explicit `--out` path for an explicit `--scenario`.

Ports are discovered with Node built-ins only: a temporary
`net.Server` bound to `127.0.0.1:0`, the assigned port read back, the listener
closed. Two ports are taken and checked to be distinct. No dependency was
added.

Closing the probe is unavoidable, and it means a port is only known-free at the
instant it is chosen; nothing can reserve a TCP port without holding it open.
The contract is therefore generated immediately before each run, and that
constraint is documented in the demo README.

`--demo-port` and `--viewer-port` pin the ports for deterministic debugging and
for the generator's own tests. Generated contracts carry absolute paths and
live ports, so none are committed; only the generator is.

The contract declares a `demo-server` process with an HTTP readiness probe on
`/health`, an `observer-viewer` process with a readiness probe on
`/api/status`, and an `applicationUrl` pointing at the viewer, which is the
application the tutorials drive. Both processes use `cwd: "target-root"`, and
the viewer is started without `--root` so the project-aware session discovers
the prepared project itself.

## 10. Prepare/bootstrap lifecycle

`examples/v09-demo/scripts/prepare-tutorial-target.mjs` is the contract's
trusted prepare executable. It runs once and terminates; it never becomes a
server.

In order:

1. validate `--target-root`, `--scenario` and `--demo-port`;
2. materialize the demo by calling Prompt 1's own `prepareDemoTarget`, so no
   second demo-copy implementation exists;
3. start Prompt 1's `startDemoServer` in process on the same `demoPort` the lab
   will later use;
4. `node dist/cli.js init` with the demo URL, the 1440x900 viewport and a
   targets file;
5. `node dist/cli.js capture baseline`;
6. scenario-specific evidence;
7. stop the temporary server in a `finally`.

The temporary server exists because Observer's canonical `init` and `capture`
need a live loopback target. Stopping it in a `finally` means a failing prepare
still releases the port, which a test verifies by rebinding that exact port
after prepare returns.

Every artifact comes from a canonical owner. Prepare authors contract JSON only
as *input* to `approve-baseline` and `save-change-contract`, which are what
validate and persist the artifacts; it never writes an artifact manifest
itself.

## 12. Contract activation setup

contract and saves an initial change contract through the canonical commands,
then writes project acceptance.

The acceptance block is written through the canonical
`validateProjectConfig` owner: the configuration is read, extended,
revalidated and only then written back, so an invalid acceptance block can
never reach disk.

One correction was needed during implementation. `--output` names a *parent*

persisted paths are now read back from the CLI's own `Artifact:` output and
